Serverless CloudOps Data Platform

Complete 6-Week Engineering Theory & Technical Interview Guide

System Architecture

Project Big-Picture Overview

You built an Event-Driven Serverless Data Pipeline Platform.

In plain English: Whenever a feedback ticket (a JSON text file) is uploaded to an AWS cloud storage bucket (S3), three automated microservices (AWS Lambda) wake up in milliseconds. They validate the ticket, categorize whether it is a bug, feature request, or complaint, score its priority, store it in a database (DynamoDB), archive a backup copy, and send live metrics to a real-time monitoring dashboard (Grafana) — engineered strictly to cost $0.00 / month.

Week 1

Cloud Foundations & Infrastructure as Code (IaC)

Key Services & Concepts:

  • Infrastructure as Code / IaC: Writing machine-readable config files to define cloud resources instead of clicking buttons in web consoles.
  • Terraform (HashiCorp IaC Tool): Declarative engine that provisions and manages cloud resources automatically.
  • Amazon S3 (AWS Simple Storage Service): Highly durable object storage. Created 2 buckets: raw-inbox (ticket drop zone) and processed-archive.
  • Amazon DynamoDB (AWS Serverless NoSQL Database): Fast, managed key-value database configured with PAY_PER_REQUEST billing for $0.00 idle cost.
  • AWS IAM (Identity & Access Management): Security service managing roles, policies, and permissions using the principle of least privilege.
  • AWS Named Profiles: Local CLI configuration mapping project credentials to an isolated profile name (tickets).

Core Terraform Files:

provider.tf (AWS provider & region), variables.tf (reusable params), main.tf (S3 & DynamoDB resources), outputs.tf (prints resource names on completion).

Week 2

Event-Driven Serverless ETL Pipeline

Key Services & Concepts:

  • Serverless Computing: Running code on-demand without provisioning or paying for idle virtual servers.
  • AWS Lambda (Serverless Compute): Event-triggered microservices executing business logic in milliseconds.
  • Event-Driven Trigger: S3 detects an s3:ObjectCreated:* event on JSON upload and invokes Extractor Lambda automatically.
  • Boto3: Official AWS Python SDK allowing Python code to interact with S3, DynamoDB, and Lambda.

The 3 Lambda Microservices:

  1. Extractor (extractor/handler.py): Triggered by S3 upload $\rightarrow$ parses JSON $\rightarrow$ validates required fields (user, email, issue) $\rightarrow$ async invokes Transformer.
  2. Transformer (transformer/handler.py): Heuristic keyword analysis $\rightarrow$ assigns Category (bug, feature, complaint) $\rightarrow$ assigns Priority (high, medium, low) $\rightarrow$ generates UUID Ticket ID $\rightarrow$ async invokes Loader.
  3. Loader (loader/handler.py): Writes record to DynamoDB $\rightarrow$ archives JSON copy to S3 partitioned by date (processed/YYYY/MM/DD/ticket.json).
Week 3

Containerization & AWS ECR

Why Containers for Lambda?

  • Overcomes Size Limitations: ZIP files are capped at 250 MB; Container images allow up to 10 GB payloads.
  • System Dependencies: Ability to include custom OS-level packages and libraries.
  • Unified Standard: Same packaging format across Lambda, ECS, and Kubernetes.

Services & Debugging Journeys:

  • AWS ECR (Elastic Container Registry): Private container repository.
  • Docker Layer Caching: Base Python images cached across builds, speeding up subsequent builds from 77s to 2.5s.
  • Bug 1 (IAM Authorization): Added AmazonEC2ContainerRegistryFullAccess to fix ecr:CreateRepository denial.
  • Bug 2 (Windows Pipe Line Endings): PowerShell stdin pipe mangled token bytes. Resolved with docker login -u AWS -p (...).
  • Bug 3 (OCI Image Manifest): AWS Lambda rejected multi-arch index manifests. Fixed with --platform linux/amd64 --provenance=false.
Week 4

CI/CD Automation with GitHub Actions

The Dual CI/CD Pipelines:

  • CI Workflow (ci.yml): Triggered on Pull Requests/Pushes $\rightarrow$ runs Flake8 linting $\rightarrow$ executes Pytest unit tests (test_transformer.py) $\rightarrow$ checks Terraform syntax format and validation.
  • CD Workflow (cd.yml): Triggered on merge to main $\rightarrow$ authenticates with AWS via GitHub Encrypted Secrets $\rightarrow$ builds Docker images with Buildx $\rightarrow$ pushes to AWS ECR $\rightarrow$ runs terraform apply -auto-approve.
  • Remote S3 Terraform Backend: Stored state file in a dedicated S3 bucket so local machines and ephemeral GitHub Actions runners share a single source of truth without resource collision.
Week 5

Observability Stack (Prometheus & Grafana)

Serverless Observability Architecture:

  • Prometheus Pushgateway: Bridge for ephemeral microservices. Lambda pushes short metric events upon finishing; Prometheus scrapes Pushgateway on a recurring 5s polling loop.
  • Prometheus: Time-series database storing ticket metric events.
  • Grafana: Visualization UI configured with automated dashboard provisioning and custom PromQL queries.
  • Docker Compose: Runs Prometheus, Pushgateway, and Grafana in an isolated local bridge network (monitoring-net).
Week 6

Automation Scripts & Final Polish

  • simulate_traffic.ps1: Automated PowerShell load generator simulating realistic tickets into S3 and metrics to Grafana for interview demonstrations.
  • teardown.ps1: Empties S3 buckets and executes terraform destroy -auto-approve for a zero-spend guarantee.
  • README.md: Complete repository documentation with workflow badges, ASCII diagrams, and quickstart commands.

Interview Prep

Top 10 Technical Interview Questions & Answers

1. Why did you choose AWS Lambda over running on an EC2 instance?

Answer: Cost, scalability, and operational overhead. An EC2 instance incurs cost 24/7 even when idle and requires OS patching and scaling group management. Lambda is completely serverless — it scales from zero to thousands of concurrent executions automatically, runs only when a ticket arrives, executes in milliseconds, and fits completely within the AWS Free Tier (1M free requests/month).

2. Why did you containerize your Lambda functions instead of using standard ZIP files?

Answer: Standard Lambda ZIP deployments have a 250 MB unzipped size limitation and restrict you to AWS's pre-configured runtimes. Container images allow up to 10 GB payloads, enabling custom system libraries and heavy machine learning dependencies, while standardizing our packaging format across Lambda, ECS, and Kubernetes environments.

3. Why did you need Prometheus Pushgateway instead of having Prometheus scrape Lambda directly?

Answer: Prometheus uses a pull model, scraping long-running target endpoints every 15–30 seconds. Lambda functions are ephemeral microservices that spin up, execute in 500 milliseconds, and terminate. Pushgateway acts as an intermediary metrics cache — Lambda pushes its metric event upon completion via HTTP POST, and Prometheus scrapes Pushgateway on its standard polling interval.

4. Why is a Terraform Remote S3 Backend necessary in a CI/CD pipeline?

Answer: When running Terraform locally, state is stored in a local terraform.tfstate file. In CI/CD, GitHub Actions spins up on a fresh, ephemeral Ubuntu runner that has no local files. Without a remote backend, Terraform wouldn't know the infrastructure exists and would attempt to recreate existing resources, causing conflicts. Storing state in S3 provides a single, persistent source of truth shared between local machines and CI/CD runners.

5. How did you secure your credentials in GitHub Actions?

Answer: I used GitHub Encrypted Secrets (AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY), which are encrypted at rest with AES-256 and masked in logs. Furthermore, .gitignore was configured to block all *.csv, *.pem, *.tfstate, and .env files from ever entering source control, and GitHub's Secret Push Protection was enabled to prevent accidental leaks.

6. How does data flow through the ETL pipeline?

Answer: A client uploads a raw JSON ticket to the raw S3 bucket. S3 emits an ObjectCreated event triggering the Extractor Lambda. Extractor validates the schema and asynchronously invokes Transformer. Transformer uses heuristic keyword analysis to classify category (bug, feature, complaint) and priority (high, medium, low), generates a UUID ticket ID, and invokes Loader. Loader saves the record into DynamoDB for fast queries and writes an archive copy into the processed S3 bucket organized by date.

7. Why did you use DynamoDB instead of a relational database like PostgreSQL / RDS?

Answer: Feedback tickets are semi-structured JSON objects that map naturally to a NoSQL document model. DynamoDB is fully serverless with single-digit millisecond latency, requires zero database server administration, and offers 25 GB of permanent free storage with PAY_PER_REQUEST billing, whereas RDS instances incur hourly costs outside the 12-month free tier window.

8. What error did you encounter when building Docker containers for AWS Lambda and how did you resolve it?

Answer: AWS Lambda gave an InvalidParameterValueException: The image manifest media type is not supported. Modern Docker Desktop uses Buildx with multi-architecture OCI indexes and build attestations by default. AWS Lambda requires single-architecture Docker v2 schema 2 images. I resolved this by passing --platform linux/amd64 --provenance=false during docker build, producing clean, compatible container manifests.

9. What does your CI pipeline validate before allowing code to deploy?

Answer: The CI workflow enforces three gates: first, Flake8 lints all Python code for syntax and complexity issues; second, Pytest executes automated unit tests against the Transformer categorization and priority logic; third, Terraform CLI runs terraform fmt -check and terraform validate to ensure IaC formatting and syntax validity.

10. How do you ensure this project stays at $0.00 spend on AWS?

Answer: Every service was specifically chosen within AWS Free Tier limits: Lambda provides 1M free requests/month, S3 includes 5 GB storage, DynamoDB provides 25 GB permanent free storage, and ECR offers 500 MB storage. Monitoring is self-hosted locally via Docker Compose rather than paying for managed CloudWatch alarms. Additionally, I wrote a teardown.ps1 script that empties S3 buckets and runs terraform destroy to tear down all cloud resources when not in use.
